# 11 · 事故取证与签收（Incident Evidence & Sign-off）

## 症状
- 线路大面积故障、契约漂移、被封、桥断、证书事故等任何影响用户使用的事件收尾时，需要一份能让「下一次的人」直接接手的证据链与签收记录。没有取证的事故等于没发生过——Issue #9 的逐 IP 被封时刻至今无法精确还原（面板统计只有日粒度），就是前车之鉴。

## 适用契约
- 事件涉及的全部契约 id 与节点 id，在记录开头列明。

## 只读诊断（取证清单，事发时先抢这些，再修）
1. 时间锚：首次失败的探针时间、用户首报时间、每次操作时间（统一 JST，注明来源时钟）。
2. 双视角探针原始结果（上海/香港 sing-box 输出、ping.pe 截图或文本），不要只留结论句。
3. 面板侧：相关节点的 v2_server 完整行快照（JSON）、suzu_endpoint_changes 中相关审计行、契约 --verify 输出。
4. DNS/VX：CF 记录读回（record id + content + TTL）、VX 规则全量导出。
5. 供应商侧：实例状态、到期日、工单号与往来原文（工单措辞红线：只写 TCP 回程丢包类中性描述，绝不出现墙/GFW 字样）。

## 修复动作
- 修复按对应手册执行（01–10），本手册只管记录与签收，不另创修复路径。
- 记录结构固定：事件摘要 → 影响面（哪些契约/用户动作受影响、时长）→ 时间线 → 根因（分「已证实/推断」两栏，推断不许写成结论）→ 处置动作与每步验证结果 → 遗留项与负责人。

## 发布前检查（签收前）
- 证据清单 5 项齐全，缺项注明缺失原因（如「面板仅日粒度统计，逐 IP 时刻不可还原」要明说，不许用估计值冒充）。
- 恢复验证有原始输出存档，不是「测过了」三个字。

## 用户侧验证
- 由当班以外的视角复核一遍恢复状态（巡检号订阅字节、双视角 204、出口 IP），复核人签字（记录名）后才算签收。

## 停手条件
- 根因证据互相矛盾时：记录保持「未定性」，列出 competing 解释与各自证据，不许为了关账硬选一个。
- 涉及用户资金/账号安全（如凭据疑似泄露）：立即升级用户，取证优先于恢复。

## 回滚与审计
- 本手册产出的事故记录存入 xboard goal 的 hidden_files（参照 issue9-forensics.md 的格式），并在当班记录中留指针。审计行 id、备份路径、工单号全部写进记录正文，方便按图索骥。
